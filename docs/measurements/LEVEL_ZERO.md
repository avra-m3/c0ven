# Level Zero feature map: each need, and the call that gives it

Each mechanism the design considered, mapped to the Level Zero call or extension that provides it, with the spec
version that introduced it. Two columns give what the machine's driver reports
([record](MEASUREMENTS.md#2026-10-11-level-zero-report)) and the measurement that tested the mechanism on the
B60s. Not every row is used: the calls the engine makes are in `core/ze/ze.cpp`.

## Sources and how to read the table

- **Spec version.** Every link points at the Level Zero spec v1.15.31
  (`https://oneapi-src.github.io/level-zero-spec/level-zero/1.15.31/`). That is the spec the machine's
  compute-runtime 26.18.38308.1 was built against (its release notes), and [MEASUREMENTS.md#the-test-machine](MEASUREMENTS.md#the-test-machine) gives
  the container's API as 1.15. The version in the "Spec" column is the `version:` field of the symbol in the spec's
  own source ([oneapi-src/level-zero-spec](https://github.com/oneapi-src/level-zero-spec), tag `v1.15.31`,
  `scripts/core/*.yml` and `scripts/sysman/*.yml`). No field means 1.0.
- **Kinds.**
  - **core**: part of the API every driver of that version implements.
  - **standard extension** (`ZE_extension_*`): optional; a driver lists it in `zeDriverGetExtensionProperties` when
    it has it.
  - **experimental** (`ZE_experimental_*`, functions ending in `Exp`): optional, and may change or be dropped in a
    later spec. Marked **experimental** in the table.
  - **Intel driver experimental** (`ZE_intel_experimental_*`, `ZEX_*`, functions `zex*`): not in the spec at all.
    Defined by Intel's compute-runtime ([`level_zero/include/level_zero/`](https://github.com/intel/compute-runtime/tree/master/level_zero/include/level_zero),
    [`level_zero/doc/experimental_extensions/`](https://github.com/intel/compute-runtime/tree/master/level_zero/doc/experimental_extensions)),
    reached through `zeDriverGetExtensionFunctionAddress`. Also marked **experimental**.
  - **build option**, **environment variable**, **spec rule**: a string or a rule the spec defines, not a call.
- **compute-runtime on Battlemage.** From compute-runtime's
  [GitHub releases](https://github.com/intel/compute-runtime/releases). Each release has a "Quality expectations"
  table with the Level Zero version it supports per platform. For Battlemage:

  | compute-runtime | Released | Level Zero version for Battlemage | Spec headers it was built against |
  | --- | --- | --- | --- |
  | 24.48.31907.7 | 2024-12-24 | 1.6 (first release listing Battlemage) | 1.11.3 |
  | 25.18.33578.6 | 2025-05-20 | 1.6 | 1.12.15 |
  | 25.40.35563.4 | 2025-10-29 | 1.13 | 1.13.0 |
  | 25.48.36300.8 | 2025-12-15 | 1.14 | 1.14.33 |
  | 26.14.37833.4 | 2026-04-20 | 1.15 | 1.15.31 |
  | 26.18.38308.1 | 2026-05-12 | 1.15 (the llama.cpp image measured against) | 1.15.31 |
  | 26.31.39395.13 | 2026-08-21 | 1.17 | 1.17.24 |

  So a row's earliest release is:
  - core up to 1.6: 25.18.33578.6;
  - core 1.7-1.13, and the experimental extensions compute-runtime's
    [Level Zero release notes](https://github.com/intel/compute-runtime/blob/master/level_zero/doc/RELEASENOTES_CORE.md)
    list under v1.13 (counter-based event pools, immediate command list append, mutable command lists):
    25.40.35563.4 at the latest. The driver often shipped these earlier than it claimed the version; where a
    commit date is known it is given;
  - 1.14: 25.48.36300.8; 1.15: 26.14.37833.4;
  - Intel driver extensions: the commit that added the code, when found. Whether a Battlemage release lists it is
    "unknown" in this column; the next column gives what the machine's driver lists.

  Everything up to 1.15 is therefore in the machine's 26.18.38308.1. Things added in 1.16-1.17 (a host-function
  append, record-and-replay graphs, the standard relaxed-allocation-limits extension) are not, and are named only
  where they would replace a row.
- **Reported by the machine's driver.** Read on 2026-10-11 ([record](MEASUREMENTS.md#2026-10-11-level-zero-report))
  from the engine image's stack (compute-runtime 26.35.39758.10, loader 1.32.0, API 1.17;
  [ADR-0002](../adr/0002-pin-the-toolchain.md)), not the llama.cpp image's 26.18. Each cell is yes, no, or "not
  reportable" where no driver query gives the answer.
- **Measured in.** The measurement that tested the row on the B60s, with its question numbers (Q1, Q2 ...)
  where the record numbers them. "-" means the driver report is the only record.

## What follows from the spec

- A recorded list cannot be replayed while its previous replay may still run (row 13), so a card needs one recorded
  set per step in flight.
- The mutable command list does not give per-token values while a list runs (row 16): the spec requires the
  list's execution to be synchronised before an update. Per-token values come from memory (row 15) or indirect
  launches (row 17).
- Counter-based events cannot carry the CPU's signals (row 20): the host cannot signal them. The fallback in
  ADR-0011 is a regular host-visible event (row 19).
- One context means one failure domain (row 29). A hang or a job-timeout kill on either card invalidates the
  shared context, so both cards reload.
- Kernels that follow pointers read from memory need indirect access set (rows 8 and 26), or the driver may not
  make the pointed-to allocations resident.
- A third form of wait exists (row 22): Intel's command-streamer wait on a memory value. It holds no EU threads, so
  it has no forward-progress problem. It is a driver-private extension.
- The existing-memory import has a standard path (row 7a) as well as Intel's private one. Its pages must be
  aligned to a page size the card supports.
